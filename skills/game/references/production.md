# 制作分工、网页交接与归档

## 任务拆分

按照可独立产出的模块分工，而非按窗口数切碎句子。一个任务要有输入版本、明确范围、唯一写入对象、交付、验证点及依赖。相邻章节共享人物状态和时间节点；相邻系统共享已获准接口。候选可并行，但不能互相把未验收方案当正史。

常见角色包括章节剧本、人物关系、支线、证据时间线、地区与环境、对白演出、模式映射、技术规格、连续性审读、集成检查。按真正工作选择角色，不能为了凑十个复制同一任务。

每个任务带所需方法摘要和来源输入。安装在 Codex 的 Skill 不会自动出现在 ChatGPT 网页；网页模型无法读取本机路径时，应提供已授权的可访问内容或摘录，不让它假装读过。

## 延续项目流程

真正恢复网页开发时，再读取当前 WORKFLOW、账本、checkpoint 和明确授权。保留原有 dispatch.lock 与 control.py 预约流程，不建立第二套发送器。不因调用本 Skill 恢复暂停定时或打开旧标签。

派发需要确认正确项目、真实模型、可读空草稿、任务未发送和窗口空闲。超时先回读。已有草稿不可覆盖或自动发送；上下文上限可在授权范围新建同项目聊天并登记新旧 URL，账号级限制不能绕过。

每轮记录实际检查与发送数量、每窗口状态、任务 ID 和证据。计划、预约、发送确认、生成、交付、验收、归档是不同阶段。暂未派发就如实写原因。

## 技术交接

默认遵守当前“暂不执行游戏代码／测试”的授权；用户以后授权时更新。规格要可实现，可附候选源码，但不伪造运行结果。现有项目若是 Godot，不因资源合集偏好 Unity 自动迁移。

代码提交到正式仓库的独立 codex/ 分支和 Draft PR。核对实际文件、HEAD 与 PR 状态；不自动合并 main，不把创建 Issue 当作代码落库。公开实现用抽象 ID 或无剧情合成示例，不夹带原稿与未公开设定。

## 归档

- Notion：进度、设计决策、候选内容、来源、审读记录；沿用项目已授权位置。
- GitHub：公开技术实现、方法资料、脱敏索引及 Draft PR。
- Drive：允许归档的原件／候选／资产／证据包；保留来源和许可，按内容哈希去重。
- 本机：当前工作文件、恢复记录、任务状态及归档回执。

只对本轮实际需要的目的地进行写入，回读关键字段或正文并对照内容哈希。缺必需归档标 archive_pending；相关归档欠缺不自动阻断无依赖的设计工作。

原始材料、作者草稿和旧版本不能被新稿覆盖。对外包只包含审过的明确文件清单，不直接打包整个项目目录或个人 Skill 目录。
