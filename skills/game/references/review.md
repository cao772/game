# 审读与证据

## 先确定审读对象

结构、因果、角色与玩法先于措辞。用户仅要润色时不强行重构整部作品。先列实际读到的版本与范围；摘要、局部片段、模型自报和真实交付分开。

采用同一标准比较备选方案。每条重要问题包括：位置、原有事实或设计目标、冲突表现、玩家／读者影响、最小修订。未证实的风险写为假设，不能把个人偏好包装成硬性错误。

## 叙事检查

- 人物目标是否驱动行动，关键转折是否由已建立的选择和规则造成。
- 谁何时知道何事；是否拥有所需证据、物品、能力和行动时间。
- 地理、年龄、伤势、关系与时间顺序是否一致。
- 人物改变是否有触发和代价；配角是否只服务于解释设定。
- 前文承诺是否兑现；揭示是否能回看验证。
- 情绪是否有强弱与余波，是否用重复灾难和抽象说教取代具体生活。
- 对白是否有不同声音，是否故意隐瞒本该说清的事实。
- 新稿是否误将候选解释、角色传闻或经典作品元素写成正史。

## 可玩性检查

- 玩家动作能否改变可观察结果。
- 目标、选择风险和反馈是否可理解。
- 正常路径之外是否可达、可恢复或明确结束。
- 选择是否存在永远更好的无代价选项。
- 玩法是否支持主题，还是奖励与叙事赞扬相反的行为且没有处理这种矛盾。
- 地区、系统、资产和分支成本是否在当前制作范围内。
- 双模式、存档与重玩是否产生未声明的状态污染。

## 修复优先级

先修造成主线矛盾、知识越界、不可恢复卡关、私人资料泄漏的问题；再修动机薄弱、选择无效、节奏与负担；最后做文字与表现层。给定位、例子和修改，不只打分。

可以扮演不同读者角度检查“可能如何理解”，但必须标明是模型模拟，不能叫玩家访谈或用户测试。评分只是组织意见的工具，不把自评分高当成功证据。

## 完成声明

内容审读通过不等于代码正确；代码检查不等于游戏可玩；Windows 结果不等于 Mac 实测；性能预算不等于性能数据。输出版本、检查范围、方法、未检查部分、剩余问题。若禁止运行，就交静态分析与下一步验证点。
